# Memory Graph — Agent Warm Start

You have a persistent memory graph on this machine. Directories are memory Nodes, symlinks are Edges. You traverse it with ordinary file tools; you write to it only through the helpers in `bin/`.

- Graph root: `$GRAPH_ROOT` (default: the `memories/` directory next to this file)
- Overview of everything stored: read `$GRAPH_ROOT/MAP.md` — one line per node, `<id> — <description>`, strongest first. **Open handoffs (unfinished work left for you) pin above the list — read them before touching their thread.** A row marked `[superseded by <id>]` is history: read the named successor for what is true now. If the map looks stale, regenerate with `bin/graph-maintain`; ground truth is `grep -H '^description:' */node.md` from the graph root.

## Reading (raw filesystem — safe, use freely)

| Intent | Command |
|---|---|
| What is this node? | `cat <id>/node.md` |
| Neighbors + what they mean (inside a node) | `grep '^description:' __edges__/*/node.md` |
| Hop to a neighbor (inside a node) | `cd __edges__/<id>/` |
| Who points at this node? | `ls __edges__/` — plain edges are symmetric (one logical edge, a symlink in BOTH node dirs), so your own edge dir is the backlink list. `find . -type l -lname '*/<id>'` (from graph root) additionally finds directed in-edges (`supersedes`/`follows-from`) and not-yet-migrated single-direction edges |
| Find a node for a query | `grep -H '^description:' */node.md` (from graph root) |
| Who wrote this node, and from which chat | `bin/provenance <id> [--json] [-n N]` — read-only: the write lines (`ts op host actor session call`) from `.provenance/<id>.jsonl` |

Node IDs are opaque ULIDs — never meaningful, never renamed. All meaning lives in `node.md` descriptions.

A grep that turns up nothing on point after you have retried with the words a note would have been WRITTEN with IS the answer: say the graph does not record it — but only once the promising nodes have been followed through: search bodies too (`grep -rl '<term>' */node.md`), not descriptions alone, and open the extra files in a candidate node's dir, because a description that does not show the answer is not a node that lacks it. A node followed through and still not carrying the thing asked about is a miss like any other. Never bridge the miss with what you generally know about the system the graph covers — a plausible menu item, field, or setting supplied from world knowledge reads back as something you remembered, and is wrong exactly where the user was relying on you. Questions presuming an element exists ("what is between X and Y", "which option does Z offer") are the sharp case: when the graph covers the surrounding ground and shows no such element, "there is no such element" beats inventing one, and retrieved negative evidence (a node recording that the filter returned 0 rows) outranks generic knowledge outright. This is calibration, not reflex refusal — when the graph DID answer, answer from it plainly, and when the repository, the shell, or this conversation authoritatively answers, the miss never bars reading it. What it bars is the guess.

## Writing (helpers only — never mkdir/ln/echo into the graph by hand)

```
bin/node-new "<one-line description>" [type]   # prints the new node's ID; optional type:
                                               #   identity|preference|decision|gotcha|journal|thread|trivia|handoff
bin/edge-add <src-id> <dst-id> [type]    # connect two nodes — a plain edge is SYMMETRIC (one call links both
                                         # directions; never add the reverse yourself). Optional type:
                                         # supersedes|follows-from stay one-way; relates-to is symmetric, just named
bin/touch-edge <src-id> <dst-id>         # record that you used this edge (strengthens it); the edge must exist
bin/graph-maintain                       # regenerate MAP.md, integrity + prune + duplicate report, complete
                                         # half-edges under --apply (requires node on PATH)
```

Keep descriptions to one line, well under 500 characters — every future session pays for every description via the map. Detail goes in the node body, not the description.

For a decision, put the why in the description itself — `<choice> because <compressed why>`. The map shows descriptions only; a description that just names the choice hides the part future sessions ask about. And write dates absolute (ISO), never "yesterday"/"next week" — relative vocabulary rots the moment the session ends. Resolve them against the conversation's date, not your own: your clock is not the events' clock, and a conversation you are compacting, replaying or importing rarely happened today. Date events from the date the conversation states for itself; failing that, from one your harness supplies for it; failing both, from today — your own clock is the last resort for an event date and always the date for `created:`/`updated:` bookkeeping, never a substitute for a date the conversation states or your harness supplies. And resolving is not minting: a date or qualifier the source never STATED — a 「下周」 you anchored to a specific week, a 「无时间表」/「未定」 nobody said — is your inference, and is written as one, marked on its line (推断, or the anchor form 「下周三, 以<anchor date>为基准」); precision written bare reads back as the source's own fact. A precise value the source itself stated needs no mark — quote its words when you keep your resolution beside them.

Habits that keep the graph useful:

1. After storing a memory, connect it: `edge-add` it to the nodes it relates to. An unconnected node is nearly unfindable later. One call per relation — the edge is symmetric, so adding the reverse direction is a no-op, never a second edge.
2. After traversing an edge that helped you, `touch-edge` it once per session — access history drives ranking and pruning.
3. Inside your own node dirs you may create any extra files you want (notes, data, embeddings) — the framework never interprets or deletes them, and they follow the node through merges and supersessions. Reserved names only: `node.md` frontmatter, `__edges__/`, `MAP.md`, and the legacy name `accessed.log` (access bookkeeping now lives outside node dirs, in `$GRAPH_ROOT/.access/<id>.log` — never write either by hand). A `.node.md.prev` beside `node.md` is the framework's one-deep snapshot of the body the last rewrite replaced — recovery data, never yours to write.
4. A node has two tiers. `node.md` is the most succinct version — the gist plus the facts, decisions and reasons that must rank, since search weighs descriptions and bodies far above attached files. An extra file inside the node dir is the curated detail tier: when what you are storing carries detail beyond the gist — a complete list, a table, a full enumeration of an interface's options, an exact click or step sequence, a verbatim passage, a transcript, a code or data dump, extended reasoning — the full detail goes in that file, never in a loose file elsewhere on the machine. The split between the tiers is by kind, not by degree: the body keeps the retrieval keys at full weight — identifiers, dates, names, the file's own name, the conclusions — and the file keeps the bulk: the rows, the steps, the option lists, the enumerations, the verbatim passages. When a fact is BOTH — a table of dates, a list of ids, a roster of names — the complete set is bulk and stays in the file; the body keeps only its range, its count, the one or two load-bearing members, the conclusion. Restating the file's rows in the body buys nothing, because a search hit inside the file quotes the matching row back (habit 13). What must never shrink is the file — never trim it down to what the body left out. A verbatim deliverable is the sharpest case of this tier, not a separate trigger: a contiguous payload presented as an artifact's contents (a delivered report's body, a multi-row table, a recited transcript or quoted document), however short the piece in front of you, is stored whole as the extra file while the body stays the gist card (what it is, the key conclusions, the file's name) — inside dsh that is ONE call, `memory_write` with `attach: {filename, content}`, never a write followed by a separate attach (habit 13). Summarizing a document you could have attached loses the document — a deliverable compressed into body prose cannot be re-served when the user asks for it back. Name the file for what it contains (`magento-orders-grid-columns.md`, `周报-2025W32.md`), never `attachment.md`/`notes.md`/`details.md`: the filename is the handle the user asks by. Ordinary dialogue has no detail tier: a passing remark needs no file.
5. When new information CHANGES a stored decision, do not rewrite the old node. Make a successor and mark the old one: `node-new` the new decision, `edge-add <new> <old> supersedes`, then prepend one line to the old node's body: `Superseded by <new-id> on <YYYY-MM-DD>.` — every surface then marks and deranks the old node while its rationale stays readable. Reserve in-place edits for typos and details; when you do revise a body, `cat <id>/node.md` first — a body rewritten from what you remember of its description line silently drops every fact you did not remember — and stamp `updated: <YYYY-MM-DD>` in the frontmatter.
6. Never blank or rewrite a node to DELETE something the user asked to store — an in-place edit keeps no history. Retire a fact with the supersede pattern above; whether to truly discard a stored value is the user's call.
7. A durable user preference, output-format rule, correction, or standing reminder is ALWAYS stored — "retrievable elsewhere" never exempts a rule about how the user wants you to behave, because rules live in how the user talks, not in any record you could retrieve later. Give it its own `preference`-typed node (a bullet buried in an unrelated thread node never generalizes), and when the user retracts or corrects one ("not X — actually Y"), store the corrected version as a successor (`node-new` + `edge-add <new> <old> supersedes`, step 5's pattern) — never re-merge the withdrawn version, and never rewrite the old node in place.
8. A tool result you cannot see — archived, truncated, elided, or still pending — is an UNKNOWN, not something you learned. Store the open question ("searched X on <date>; result not seen"), never a reconstruction of what the payload plausibly said; if you cannot quote it from the source in front of you, you do not know it. A segment mixing visible prose with elided results is not unusable: store the visible facts, store the elided parts as open questions. And a memory-update pass with durable content always ends in a write — when nothing certain emerged, write ONE node naming what the conversation covered and which questions it left open; when everything is already stored, revise or link the covering node by id — recording at least that it was re-confirmed and when — instead of restating it, no-op-writing it, or exiting silently. Only a segment with nothing durable at all — pure pleasantries, a one-off task leaving nothing behind — ends without a write, and never with a node whose only content is that there was nothing to store. Close the pass by reporting the writes you actually made, by id, from the tool results — never narrate against them.
9. Leaving work unfinished? Write a `node-new "<pending / blocked-on / next step / owed>" handoff` — it pins atop MAP.md until closed. Close a finished handoff by superseding it with the outcome (or change its `type:` to journal/thread if it should stay as plain history). One open handoff per thread: revise the existing one rather than minting a second. And unfinished work is not only your own leftovers — in-flight work you merely learned about (a report the user is still owed, a worker return that came back empty or truncated and needs re-delivery, a re-dispatched query, an unanswered question, a cancelled task) is durable work state too: record it in the same pending/blocked-on/next-step/owed shape (`thread` for ongoing state, `handoff` only when the next session must pick it up), and when a later session shows it delivered or dropped, write that back so the map never asserts stale open work. Every pending item carries its identifiers verbatim (step 10) — a worker id is what makes the item resumable, and an item stored without one can be neither re-polled nor fetched, only described. Storing the result in a NEW node does not close the old item: in the same session, sweep the open handoff/thread nodes that track it and mark that item delivered or drop the line — a pending list that survives its own resolution is a lie.
10. Identifiers are content, not bookkeeping. When a fact you are storing names one — an artifact id for a delivered report, a file or recording id, a task or ticket number, the deliverable's own filename — copy it into the body exactly as it appeared, and into the description when it is the natural handle for the thing. They are the highest-precision retrieval keys the graph will ever hold: exact-match tokens that survive paraphrase, which is precisely where description grep is weakest. So an id is never the "too much detail" you trim into an attachment — it is already the shortest possible form of the fact it names — and never something to reconstruct from memory: copy it, or record that it is unknown (step 8). Store the user's own name for a thing beside the canonical one ("用户说的'Common工序拆分'即指此场会议"), or the words they will search with are nowhere in the node.
11. Run `bin/graph-maintain` occasionally; it never deletes anything without `--apply`. Edges whose access history has gone stale are prune candidates; edges with no history are never auto-removed. Its duplicate report suggests merge pairs — decline any pair wearing a `[superseded by]` marker; that is history, not duplication.
12. A status line about what YOU, the assistant, did — searched, found nothing, told the user, could not generate, was corrected — must quote the conversation's own words in the line (「…」), or not be written at all. Such an event is never remembered or inferred: either the turn in front of you states it, or it did not happen (step 8's rule, applied to your own behaviour). When a turn reads an open handoff/thread and resolves nothing, the correct write-back is exactly one appended line — `状态未变（turn N 无新信息）`, with the turn's number or today's date for N — never a narrative of what must have happened.
13. If you are running inside dsh, prefer its memory tools over raw file access: `memory_search` also reads attached files — quoting back the passage it matched and the byte offset to resume reading at, so a fact the body's gist dropped comes back on the hit row itself — and tells you which query terms missed; `memory_read` with `from` records the traversal and wires the edge if missing; `memory_read_file` pages an attachment back; `memory_attach` with `from_path` copies a loose file into a node (the source is left untouched; hidden files, system paths and anything outside the deployment's allowed directories are refused); `memory_write` with `attach: {filename, content}` stores the gist card and the verbatim payload in one call (step 4); `memory_write` with `supersedes` does step 5 in one call.
